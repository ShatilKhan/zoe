# Zoe MVP implementation spec — synthetic-data hackathon build

Status: proposal only. No product code, accounts, cloud resources, or commits were created.
Research date: 17 November 2026. The Presage challenge deadline is 22 November 2026.

## 1. Product decision

Zoe is a patient-controlled record book. A patient can record conditions, allergies, medicines, visits, prescriptions, and reviewed meals. They can ask natural questions about records, medicines, diet, and nutrition, and see where each answer came from. They can share selected records with a clinician. A separate wellness screen displays live SmartSpectra pulse and breathing rates after camera consent. Zoe does not diagnose, prescribe, recommend a dose, or make a treatment decision.

The hackathon version should show one complete path: sign in → add a record or prescription → review extracted text → ask a spoken or typed question with sources → start and stop a live pulse and breathing session → share selected records. A clinician can sign up and read an invited record set. Clinician identity is self-declared in the prototype; it must not appear as verified.

“Can I take this medicine?” is an **in-scope question**. Zoe should answer it in natural language with confirmed record facts, matched medicine-label evidence, and clear gaps. For example, it can point out a recorded allergy and the exact label warning, then suggest a pharmacist or clinician check before the patient acts. It must not turn incomplete evidence into an all-clear, a personal treatment decision, or a numeric risk score. This boundary follows the challenge ban on medical decision-making; it does not ban the question.

## 4. Proposed architecture: one build path

**Decision for this MVP:** Build one Android-first Expo SDK 58 app as an internal-distribution **preview APK**. Use React Native and TypeScript for screens. Use a local Kotlin Expo module for SmartSpectra. Use React Native ExecuTorch 0.10.6 for both PP-OCRv6 Small and Qwen3 0.6B. Use `expo-speech-recognition` with required on-device Android recognition for the chat mic. Store records in Expo SQLite with SQLCipher. Bundle a curated offline food catalog and calculate nutrition in a pure TypeScript package. Use Supabase Auth, Postgres, private Storage, and one Edge Function for identity and encrypted sharing. Build a small React clinician viewer as a static site on Cloudflare Pages. Use npm workspaces and Turborepo in one repository. Do not scaffold a second app stack or switch OCR or model runtimes during the challenge.
Use `expo-observe` in the internal APK to measure startup, selected coarse feature events, JavaScript errors, and native crashes during the owner's **synthetic-data phone test**. Expo Observe is an operational telemetry service; it is separate from Presage SDK telemetry, which stays disabled.

The choice assumes that encrypted share bundles and minimal account/share metadata may leave the phone. **Readable records, original prescription images, OCR text, model prompts, and model output stay on the patient's device.** A chosen share can contain selected confirmed facts and an optional patient-reviewed redacted image copy. After a share, the clinician's browser can read only the selected bundle. Supabase sees ciphertext and account/share metadata. This is a material privacy limit; an OAuth provider also sees the sign-in identity. If the privacy rule forbids even ciphertext upload, link sharing is impossible in this design and must be removed from the product requirement.

### Data flow and trust boundary

```text
Patient Android app
  camera -> SmartSpectra Kotlin module -> live pulse/breathing/quality card (no frame save)
                                        -> Save reading -> SQLCipher vault (only on patient action)
  photo -> local PP-OCRv6 pass -> suggested Rx region -> patient adjustment -> structured review form
  no photo -> Add medicine form -> patient-reported fact
  corrected OCR name -> encrypted per-account suggestion lexicon (no weight update)
  mic -> offline Android speech service -> editable chat draft -> patient sends
  confirmed facts + original image -> SQLCipher vault
  question -> local fact search + local label pack -> Qwen3 answer -> source/safety check
  meal text -> local food match + confirmed portions -> deterministic nutrient totals -> Qwen3 explanation
  selected facts + optional reviewed, raster-redacted image -> local AES-256-GCM bundle -> ciphertext upload
  coarse QA events/errors/performance -> Expo Observe (test build only; no PHI)
                                    |
                         Supabase private Storage
                         Postgres: IDs, expiry, grant, audit only
                         Edge Function: check JWT + grant, return ciphertext
                                    |
                      clinician React viewer (Cloudflare Pages)
                      key from URL fragment -> browser Web Crypto decrypt
```

### Technical component interaction

The [HTML technical map](proposal.html#technical) separates build tools from runtime components. npm workspaces install the mobile app, clinician viewer, pure packages, and Kotlin Expo modules under one lockfile. Turborepo orders local type checks, lint, and tests. EAS Build produces the Android APK; Supabase CLI applies database and Edge Function changes; Wrangler publishes the static viewer. These tools do not process patient questions at runtime. Expo SDK 58 autolinks native modules and aligns Metro resolution with the monorepo native dependency graph.

### Build secrets with Infisical

**Select Infisical for developer-held secrets**, with its CLI already present in this workspace. Its free cloud plan currently allows five human or machine identities and unlimited projects. Use the dedicated Zoe `dev` environment for the Presage demo key and deployment credentials, with staging/production separated. `infisical run -- <command>` can inject local process variables without writing a plaintext `.env`. If CI is added, prefer a GitHub Actions OIDC machine identity over a long-lived CI secret. The dedicated Zoe Infisical project exists; never copy secrets into the repository or a knowledge file.

An EAS **cloud** builder does not inherit the local developer's `infisical run` environment. Copy or sync only approved build inputs into EAS's preview secret variables, and use the preview build profile's `environment` field. Keep the Supabase service-role key in the Edge Function secret store; keep Expo and Infisical tokens, deployment credentials, and the local vault key out of the APK. Supabase URL and public client key may be in app config. The Presage API key for a sideloaded demo is a special limit: if the SDK needs it at runtime, build-time injection prevents a Git leak but **does not hide it from someone who extracts the APK**. Use the least-privileged, short-lived demo credential permitted by Presage, do not publish the APK, and rotate it after the demo. Infisical is not the patient-data encryption layer or a runtime dependency.

Sources: [Expo monorepos](https://docs.expo.dev/guides/monorepos/), [Expo autolinking](https://docs.expo.dev/modules/autolinking/), [ExecuTorch 0.10.6 release](https://github.com/software-mansion/react-native-executorch/releases/tag/v0.10.6), [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security).

The selected-share key must not enter a URL path, query string, request body, log, or analytics event. Keep it in the URL fragment, then remove it from browser history after the viewer reads it. The clinician signs in **before** opening the share link; if signed out, the viewer asks them to sign in and reopen the link rather than store the fragment key across an OAuth redirect. The clinician account is self-declared in the MVP and must not be marked as verified. The viewer must use a strict content security policy and no third-party scripts. The server can still infer that two account IDs have a share relationship.

Use `share_grants` with patient ID, clinician ID, random object ID, expiry, and revocation time. Store no diagnosis, medicine name, or record date in the cloud table. The patient uploads ciphertext to a private bucket. The clinician downloads through **one Edge Function**. It validates the caller's JWT, the grant, expiry, and revocation on each request; it retrieves ciphertext with a server-side secret and sends `Cache-Control: no-store`. Do not issue a signed storage URL for this path. Supabase reports that its authenticated storage endpoint can serve a cached file after an RLS change or sign-out. A downloaded copy cannot be revoked.

For local encryption, the app must fail closed if SQLCipher is absent. Expo documents that `PRAGMA key` can silently do nothing when the binary lacks SQLCipher. Keep the key in SecureStore, namespaced by authenticated user ID. Do not promise backup or recovery in the MVP: Android SecureStore values are lost on uninstall. Limit the demo to synthetic records. A separate small Kotlin crypto module can encrypt share bundles with AES-256-GCM; the browser uses Web Crypto to decrypt. Use one versioned envelope with random IV, key ID, and authenticated metadata. Do not design a custom cipher.

### Presage build and key constraint

Presage 3.5.0 documents Android `minSdk` 28, compile SDK 36.1 or later, AGP 8.10.1 or later, and Kotlin 2.2.x. Expo SDK 58's default compile SDK is 37, and its modules tooling supports AGP 9. These published constraints make the Expo internal-distribution APK the selected path, but a successful build is still a required acceptance check. The local module owns camera lifecycle and sends only requested metric samples, timestamps, stability/confidence, validation feedback, and errors to JavaScript. For the first screen, request `PULSE_RATE` and `BREATHING_RATE` explicitly rather than whole bundles. Retain the last valid sample only while its timestamp is fresh; clear it on stop or restart. A pulse estimate uses about 12 seconds; breathing rate needs about 30 seconds and a stationary camera with chest visible. Add HRV and one small waveform view to the **same capture flow** after the first phone build works: HRV needs a 60-second stable window, so the short check-in still works without it. This is a feature increment in one architecture, not another SDK trial. Disable Presage telemetry before readiness and measurement. Presage still needs network access for subscription validation.

The patient may save the displayed stable pulse and breathing values, timestamp, and SDK provenance into the encrypted local vault. HRV joins that saved reading only if the 60-second value is stable. Do not store video, face landmarks, or raw waveforms. Sharing a reading is an explicit selected-record action and uploads only an encrypted bundle.

### PII and telemetry boundary

Zoe cannot encrypt an SDK telemetry event before the SDK creates and transmits it. Set `enableTelemetry = false` **before** device readiness and capture; verify it in the native bridge and an instrumented network check. Presage authentication and subscription validation still contact Presage. Do not enable Presage LLM Insights: it sends buffered vital metrics and optional prompt text to Presage and its LLM. For Zoe-owned events, allow only coarse event names and failure codes; exclude patient IDs, record text, medicine names, transcripts, metric values, and model prompts. Encryption in transit alone does not hide readable content from a service operator. Encrypt local saved readings and selected share bundles before any Zoe cloud upload. Sources: [Presage telemetry](https://smartspectra.presagetech.com/docs/telemetry-and-privacy/), [Presage LLM Insights](https://smartspectra.presagetech.com/docs/llm-insights/).

Presage's Android troubleshooting guide says OAuth is documented for Play Store releases, while local and sideloaded builds use an API key. The hackathon build therefore uses a private, limited API key injected during build. Do not commit it or publish the APK. Rotate it after the demo. The public repository must tell each developer to use their own key. Do not present a client-embedded API key as a production security design.

## 5. OCR and record assistant: one implementation

**OCR:** Use PP-OCRv6 Small through React Native ExecuTorch. Run one local pass on the imported image, use returned line boxes to suggest the prescription area, and allow the patient to adjust it. Its output is a draft. Show the original image beside the proposed fields. The patient confirms every medicine name, strength, instruction, date, and prescriber before save. A blank field means unknown. The current PP-OCRv6 language list does not establish Bengali support, and its performance on these handwritten prescriptions is unmeasured. Train and evaluate its recognition component on licensed, reviewed medicine-line images as described below. For Bengali or unresolved handwriting, the patient types the fields. This is a supported input path, not a second OCR app build.

**Prescription region and privacy mask:** The supplied examples show blurred headers, distant writing, and medicine lines in different parts of the page. A fixed lower-page crop would miss information. After the local OCR pass, propose one or more **Keep Rx text** rectangles from text-line boxes. Let the patient adjust them on the original and inspect all detected lines before confirming. Use `expo-image-manipulator` for optional local rotation, crop, or a second targeted pass when the first pass missed a line. Highlight OCR line polygons and show confidence as a review cue; confidence is not proof that a medicine name or dose is correct. If the photo is too blurred or small, ask for a new photo or manual transcription. Never complete a drug name from a likely brand or nearby label text.

The mask has two outputs. (1) An optional second working crop can limit what the OCR model sees, but the initial full-image pass has already happened. Measure any second-pass latency and memory gain on the target APK. (2) An **optional share image** covers every pixel outside the confirmed Keep regions with opaque blocks. The patient can add blocks inside a region for names, phone numbers, clinic identifiers, or other private text, then must inspect the final image at full size before Share. Use a small Android bitmap operation in `modules/prescription-mask` to burn blocks into a new raster image and strip metadata. A transparent UI overlay or reversible blur is not a redaction. Never upload the original image, unmasked thumbnails, or OCR text as a by-product of image masking. Keep the original only in the encrypted local vault; a photo already in the phone gallery remains under that gallery's control.

Do **not** claim that Zoe can automatically identify every non-prescription field. The app proposes Keep regions but covers everything **outside the patient-approved regions** in an optional share copy. It must not silently reveal or upload any region. The full-image OCR pass does not save compute by itself. Store each confirmed field with its source crop, `OCR draft` or `manual` origin, and review status. A medicine question can use only confirmed fields. If medicine name or strength is unknown, Zoe asks the patient to check the paper, packaging, or a pharmacist; it does not give an all-clear.

**Structured manual entry:** The same form serves a new medicine and correction of one OCR row. Required for a usable medicine fact: the exact name as read from the paper or package, a source (`patient-reported`, `photo-transcribed`, or `pharmacist-confirmed`), and explicit patient review. Strength with unit, dosage form, route, schedule, duration, start/stop dates, prescriber, and note are separate optional fields with an `Unknown` state. Do not infer a missing dose or convert a brand into an active ingredient without a verified catalog match. Show the source crop beside the form when one exists. Allow Save as an incomplete record; it remains queryable as an incomplete record, and Ask Zoe must name the gap. A patient correction never changes an older record without an explicit edit and audit entry.

**Local correction loop:** Store an OCR draft, the corrected name, its source crop coordinates, and review status in the patient's encrypted vault. A small per-account lexicon can rank previously confirmed spellings as **suggestions** in later forms; it must show the source and cannot auto-confirm a new prescription. A correction of one drug does not establish that another similar handwritten word is that drug. Do not update Qwen3 or the phone's OCR weights after each save. React Native ExecuTorch documents on-device inference and custom model loading, not a ready-made on-phone training path. Patient corrections would be **supervised transcription labels, not reinforcement-learning rewards**, and would need separate consent, privacy review, and adjudication before any central training use; the MVP sends none to a training service.

**Selected OCR training track:** Fine-tune the **PP-OCRv6 Small text recognizer** off-device on licensed and privacy-audited medicine-line crops, while keeping the selected Expo/ExecuTorch app architecture. Do not fine-tune the assistant LLM for OCR. The suggested region handles review focus; annotate exact line polygons and text for each medicine name, strength, and instruction. Have two readers transcribe difficult lines and a qualified reviewer resolve disagreements; mark irrecoverable blur `illegible` rather than create a guessed ground truth. Include common and rare medicine spellings, handwriting styles, phone blur, rotations, and numeric dose/unit confusions. Supplement with synthetic line images only if they improve a real held-out set. The user-provided 600-image collection and the Bangladesh bilingual set need a license, consent, residual-identifier, and label-quality audit before training. A document count is not a count of usable labeled text-line crops.

Freeze train, validation, and test groups by **prescriber/handwriting style and document source**, not random line, so one writer cannot leak into both train and test. Keep the final test set sealed. PaddleOCR's older general fine-tuning guide recommends at least 5,000 recognition samples when the character dictionary stays fixed; it is guidance, not a guarantee for PP-OCRv6 or medical handwriting. Train from a published checkpoint, keep the Latin character set for the first pass, and record model/data hashes. Bengali-script recognition needs a separate charset and substantially more labeled data; do not claim it from a Latin fine-tune. Export the chosen checkpoint to a `.pte` that matches the React Native ExecuTorch OCR pipeline's shape, dtype, charset, and preprocessing contract. Verify that contract and real phone memory/latency **before replacing** the stock model in the single app. A successful training run alone is not a deployable mobile artifact.

**Local zero-cost capacity:** On 17 November 2026, `nvidia-smi` worked **outside the sandbox** and reported an NVIDIA GeForce RTX 3050 Laptop GPU with **4,096 MiB VRAM** and driver 595.99.02. The machine has an AMD Ryzen 7 4800H (8 cores / 16 threads), about 22 GiB RAM, and about 688 GiB free on the workspace filesystem. The earlier driver failure was a sandbox device-access limit, not a host driver failure. These specs do not prove that this particular checkpoint, optimizer, input width, and batch fit in 4 GiB; test memory and throughput with a short calibration run **when implementation starts**. For a local run, start with batches of 1–4, gradient accumulation for a larger effective batch, and mixed precision only if supported and stable in the chosen Paddle configuration. Save resumable checkpoints and training logs on the local NVMe, not the 12 GiB `/tmp` memory filesystem. Schedule an overnight run only after rights, line labels, group splits, and the export contract are ready. Do not promise that one night will reach the accuracy target; annotation quality and coverage may dominate compute.

**Free hosted compute:** The **same** PP-OCRv6 Small training definition can run in Kaggle Notebooks after every training image passes the rights and identifier audit. Kaggle announced that its P100 option retired on 15 September 2026; use its **T4×2** option, with 16 GB VRAM **per GPU**. A single-GPU training job has 16 GB, not a pooled 32 GB. The selected plan does not require Colab Pro, a GPU rental, a paid OCR API, or a hosted fine-tuning service. ## 6. Medicine information and interface

Do not crawl MedEx. Its terms forbid automated extraction without express written consent. MedEasy is a retail source and should be a link, not a drug-safety corpus. Add a **local medicine-name lookup** before the manual medicine form and as an optional OCR correction aid. The leading Bangladesh catalog candidate is BDMedData, published on 14 November 2026 from the DGDA registry. Its paper reports over 50,000 entries, five JSON files of about 14.47 MB, brand, generic composition, strength, form, human/veterinary category, and a CC0 dataset license. Before bundling any rows, verify the live download/license, DGDA source rights and provenance, update age, field quality, duplicates, and ambiguous brand-to-ingredient mappings. Keep the index and patient query on the phone. Show possible matches; require the patient to compare name, strength, and form with the package or Rx. No automatic conversion of a blurry OCR guess into a confirmed medicine.

### Diet, nutrition, and chat design

Use the same on-device `AskZoe` chat for meal and diet questions. A **pinned, curated offline subset** of USDA FoodData Central supplies food IDs, source release, units, and per-100 g energy, protein, carbohydrate, fat, and fiber. Its data are public domain; download and curate the subset during development, then ship it in the APK. The phone does not send patient meals to the USDA API. The Bangladesh Food Composition Table is useful for source comparison and local food names, but its redistribution terms need review before any rows are bundled. A generic US food may be a poor match for a Bangladeshi mixed dish; show an estimate or ask for ingredients rather than claim an exact value. Do not use model-generated nutrient numbers as source data.

**Answer route:** detect the user's intent; retrieve only relevant confirmed record facts and food entries; parse meal items and amounts as a draft; let the user correct food and portion chips; convert quantities to grams and calculate nutrients in `packages/nutrition`; pass calculated values, source IDs, assumptions, and any relevant allergy facts to Qwen3; validate the final reply against those values and IDs. If the portion or food match is unclear, ask one useful question and show no precise total. For a general diet question without a meal, use selected MedlinePlus public-domain health-topic summaries and app-authored guidance; link to WHO guidance instead of bundling its website text without a rights review. Avoid invented individualized calorie targets. A condition-specific question remains answerable: cite known record facts and reliable general guidance, state what is unknown, and refer a personalized treatment diet decision to a clinician or dietitian. Do not issue a restrictive therapeutic plan or say a food is safe for a particular allergy without enough evidence.

**Prompt contract:** Give the model its role, allowed evidence, output schema, and refusal/fallback boundaries in a versioned system prompt. Keep retrieved records, OCR text, and food descriptions in a separate untrusted data block; embedded instructions in those sources have no authority. Use the model for wording and clarification, not unit conversion, arithmetic, food identity guesses, or final medical decisions. Target Qwen3's documented non-thinking mode for a short on-device response and verify that the ExecuTorch chat template exposes the switch; a small model's speed and faithfulness must still be measured on the target phone. Retain only the recent turns and user-confirmed state needed for a reply. Do not silently add chat claims to the medical record. On an invalid source, unsupported number, or unsafe instruction, show a short evidence-grounded fallback and a next step. Prompt engineering alone is not the safety mechanism: typed inputs, deterministic calculations, source validation, and a fixed evaluation set carry that work.

**Chat UI:** The composer has a mic button that inserts editable text in place, without a separate voice screen. The patient edits the transcript in that bar and taps Send. Show starter prompts and a short capability statement. A meal answer uses compact, app-owned cards: editable food and portion rows, estimated nutrients with units, source and assumptions, and an explicit **Save meal** action. A medicine answer shows record and label evidence cards. Answers lead with a direct plain-language response, then show supporting facts and one useful follow-up. Let users correct a match or report an unhelpful answer; do not make the assistant look like a clinician. Use neutral language around food and weight. Show uncertainty near the affected number, not only in a generic footer.

### Conversation routing and edge cases

**Every Send has a terminal result.** Trim whitespace and normalize Unicode without changing medicine names or units. Empty text does not send. Give each accepted message an ID and exactly one response state. A small, deterministic fast path handles a *whole-message* greeting, thanks, goodbye, and “what can you do?” in English and tested Bengali forms. “Hi” can reply at once without loading Qwen3 or searching records. A message such as “Hi, can I take amoxicillin?” is substantive and must reach the medicine path. Do not use a prefix match that hides the rest of a sentence.

**Intent routing contract:** For every substantive message, use the same on-device Qwen3 0.6B model for one short, structured classification call. Keep whole-message social replies as a deterministic fast path. The route parser returns a *set* of task labels, the text span for each task, an urgency flag, a referent status, and missing information. The fixed task labels are `record_read`, `record_write_request`, `prescription_import_or_correction`, `medicine_question`, `symptom_or_health_question`, `food_or_nutrition`, `wellness_vitals`, `share_or_clinician`, `app_help`, `social`, and `out_of_scope`. `social` is a task only for a standalone social message; a greeting before a question does not replace its substantive route. A route may contain two or more labels; it must preserve each part of the user's request. `urgent_possible` is a separate safety flag. A medical question may be urgent even when the main task label is `medicine_question`. The parser may propose a medicine name or food item, but that text is unconfirmed until the user or a trusted local record supplies it.

Before the model call, run a small, reviewed list of urgent phrases and whole-message social phrases in English, Bengali, and tested Banglish spellings. The urgent check has priority. Its output can raise an urgent flag; it cannot clear a concern that the model detects. Use recent *confirmed* conversation state only for a pending clarification or a direct referent such as “that tablet.” Do not pass the whole chat history into the router. Imported records, OCR text, and model output cannot change the route rules. Validate the structured result against a local schema and allowed labels. Reject an empty or malformed result, an unsupported side-effect request, or a referent that is absent from confirmed state. Ask one focused question in these cases. Do not treat a model-generated confidence number as a calibrated probability. No route result can save a record, start a share, book a clinician, or tell the patient that a medicine is safe; those actions have separate checks and explicit user confirmation.

The classifier should use a versioned prompt with concise label definitions and examples of greeting-plus-question, multi-intent, urgent language, and unclear follow-up. Target Qwen3's non-thinking mode if the phone runtime supports the documented switch. Run one bounded parse per accepted message, then retrieve and answer each valid task in order. The safety route can interrupt this sequence. If classification exceeds its measured time budget, fails schema validation, or points to two incompatible actions, end in `needs-clarification` or a visible failure with Retry. Keep the original text editable. This is the selected design; a separate classifier or hosted routing service is outside the MVP.

| Message | Expected route | Required behavior |
| --- | --- | --- |
| “Hi” | `social` | Reply locally; do not load the model or read the vault. |
| “Hi, can I take this tablet?” | `medicine_question`; referent unresolved unless a confirmed tablet is current | Check the confirmed referent or ask which tablet. Preserve the medicine question. |
| “How many calories in rice, and is it okay with my allergy?” | `food_or_nutrition` + `symptom_or_health_question` | Estimate only after portion and food match; use confirmed allergy facts; do not give an all-clear. |
| “I cannot breathe. Also show my pulse.” | `symptom_or_health_question` + `wellness_vitals`; `urgent_possible` | Put urgent care direction first; do not wait for a sensor reading. |
| “Save that I take 20 mg” | `record_write_request`; medicine unresolved if no confirmed current item | Ask for the item and require form review before any write. |
| “What about it?” after account switch | Referent unresolved | Ask which item; never use the prior account's state. |
| Off-topic text that mentions “doctor” or a pasted instruction to override rules | `out_of_scope` or relevant user task only | Do not grant access, follow pasted instructions, or invent a clinical task. |

Strong intent routing is a measured product requirement, not an assumption about Qwen3. The classification design follows evidence that multi-intent queries need all sub-requests, multi-turn out-of-scope detection needs context, and hard-negative out-of-scope examples defeat simple keyword matching. Clarification is a supported outcome; Zoe does not claim the statistical coverage of a conformal method without building and calibrating one.

| Input or state | Required response | Data/model path |
| --- | --- | --- |
| `Hi`, `Hello`, Bengali greeting, thanks, goodbye, or “What can you do?” alone | Brief natural reply with one optional capability prompt. Example: “Hi! I can help with your records, medicines, or meals. What would you like to ask?” | Deterministic local reply; no vault read or model load. |
| Greeting plus a real question | Answer the real question, with a brief greeting if useful. | Route full text; preserve medicine/nutrition intent. |
| Record question with no matching fact | State that the record has no matching confirmed fact; offer to add or search another item. | Local retrieval; no invented personal fact. |
| Ambiguous medicine, meal, portion, pronoun, or two plausible routes | Ask one specific clarification with suggested choices. Do not claim a precise answer. | No unsafe guess or automatic record write. |
| General nonmedical small talk or off-topic request | Reply naturally and briefly, then offer relevant Zoe help without repeating a refusal loop. | No record access unless requested. |
| Symptom or potentially urgent language, even after a greeting | Acknowledge the concern, provide a general urgent-care direction when indicated, and avoid diagnosis or delay. | Safety route takes priority; no vital-based clearance. |
| Unsupported language, garbled dictation, huge input, or control-only text | Ask for a shorter or clearer question; retain the editable text. | Bound input length and context; no infinite parse. |
| Local model unavailable, out of memory, invalid output, or source check failure | Show a specific fallback and Retry. Offer record search or manual entry when useful. | No fabricated answer and no cloud-model fallback. |
| Patient changes account, backgrounds app, taps Stop, or sends twice | Cancel or ignore the stale generation; lock the old vault; keep one visible result per accepted message. | No cross-account context or duplicate response. |

The chat state machine is `idle → accepted → classifying → retrieving → generating → validating → complete`, with explicit `needs-clarification`, `failed`, and `cancelled` terminal states. All async stages have finite budgets set from the first phone baseline; a watchdog ends a stalled stage with Retry instead of an endless spinner. Show a progress label and Stop action during generation. Keep the draft editable while work runs, reject duplicate Send for the same message ID, and do not start parallel model generations. A completed answer keeps the source IDs and confirmed context it used. A retry starts from the same visible user message; it must not silently write or change a record. Treat retrieved record text, prescription OCR, and food descriptions as data, never as new chat instructions.

**Conversation and intent evaluation:** Prepare a development set for prompt examples and freeze a separate **200-turn synthetic holdout** before tuning: 100 single-task, 40 multi-intent, 20 ambiguous or context-dependent, 20 hard-negative out-of-scope, and 20 urgent turns. Include at least 40 multi-turn threads across those cases and at least 20 holdout examples for each high-impact label. Cover English, Bengali, Banglish, code switching, punctuation/emoji/case variants, misspelled medicine names, garbled speech transcripts, greetings with substantive questions, pronouns with and without a valid referent, repeated clarification, and account switch. Human reviewers label the valid task set, urgent flag, referent state, and whether clarification is required. Keep paraphrases and all turns from one thread in the same split; do not move holdout examples into the prompt. General intent datasets can inspire case design, but cannot establish Zoe's medical routing quality.

Report exact task-set match, per-label precision/recall and macro F1, multi-intent recall, urgent recall, hard-negative out-of-scope false-accept rate, referent/slot exact match, clarification rate, a confusion matrix, and p50/p95 route latency. Run the holdout through the native model in an Android APK; a prompt-only desktop score is insufficient. Proposed pre-demo gates on the held-out set: at least **90% exact task-set match** and **95% recall for each high-impact task** (`medicine_question`, `record_write_request`, `share_or_clinician`); **zero missed urgent cases** and **zero unconfirmed record writes, shares, or false medicine all-clears** in the fixed critical suite. A small zero-miss suite does not prove clinical safety; a miss blocks the demo path until fixed and retested. If the routing gate fails, require an explicit user choice among Records, Medicines, Meals, and Health before an answer in that area; keep the same local model and app architecture. Review every misroute, add it to regression, and rerun the untouched holdout only after a prompt or rule version is frozen. Also inject model load failure, invalid JSON, timeout, duplicate Send, Stop, and stale-account replies. Assert that every accepted message reaches a terminal visible state and that a pure greeting does not load the model or vault. Measure greeting response time on the target APK with a subsecond target; set model stage budgets after a phone baseline.

## 8. Build sequence in the selected architecture

### Preview and phone installation

Use **one app architecture with three unattended test surfaces**: browser, local emulator, and optional free Test Lab physical devices. `npx expo start --web` and Playwright check navigation, forms, chat states with synthetic fixtures, the clinician viewer, and responsive layout. Web-only adapters display a clear “sensor and local model available on Android build” state. Web preview cannot verify the Presage module, SQLCipher, Android speech service, native OCR/LLM, or phone RAM. A local KVM-accelerated **x86_64 Android API 34 emulator** runs the actual native app without the owner's phone. The selected React Native ExecuTorch package ships `x86_64` and `arm64-v8a` native libraries; configure both at the workspace root for emulator QA and the eventual phone APK. Use a Google APIs/Play-capable system image so the on-device speech-service probe has a chance to succeed, but do not assume its offline locale exists. Do not use Expo Go for the real app: it cannot load its custom native modules.

Use local `npx expo run:android` debug builds for the emulator's fast inner loop after installing the Android SDK and Java. Install a release-like **internal-distribution preview APK** from EAS on the same emulator before a test milestone; its JavaScript is bundled, so it does not need Metro. The EAS free plan currently includes 15 Android builds per month; local debug builds avoid spending that quota on every fix. For the owner, the same preview APK is direct-installable from its `expo.dev` link or QR code, without Expo Go or the Play Store. Use `eas.json` with `distribution: internal`, Android `buildType: apk`, and `uploadSourceMaps: true`; rebuild after native changes. A **Google API 34 x86_64** AVD is the first emulator target because KVM is available on this workstation, but an AVD image and tools are not installed yet. The host has an AMD Ryzen 7 4800H with SVM, usable `/dev/kvm`, about 22 GiB RAM, and ample NVMe space. Budget one emulator at a time with roughly 4–6 GiB guest RAM; do not run a heavy OCR training job alongside it. These are feasibility inputs, not a passed emulator build.

### Unattended verification and limits

**Web lane:** Run Playwright in Chrome against Expo web preview and the static clinician viewer. Use synthetic records and a preview backend or deterministic network fixtures. Assert the visible patient form, correction, chat routing, nutrition math display, encrypted-share viewer, expiry/revocation states, and mobile-width layout. Keep traces, screenshots, and console/network failures as local artifacts; redact any synthetic credentials. A web mock proves the user flow and renderer, not the Android native implementation. Do not create a second web implementation of the native sensor, vault, or model.

**Android lane:** Install the actual x86_64 APK on the local emulator. Use Maestro CLI flows for sign-in with a **synthetic preview test account**, Rx image import, crop and mask review, manual medicine entry, OCR draft correction, local chat, nutrition, share/revoke, account switch, permission denial, offline states, and app restart. Maestro drives the rendered Android UI and can save screenshots, video, logs, and JUnit-style results. Keep stable test IDs on important controls and use deterministic synthetic fixtures; a model answer is checked for required evidence and prohibited claims, not brittle exact wording. Android instrumented tests verify SQLCipher is truly linked, vault/account isolation, mask output pixels and metadata, and native module results. A **test-build-only**, non-shipping transcript injection can exercise the mic-to-editable-draft state without claiming real speech recognition; probe `SpeechRecognizer.isOnDeviceRecognitionAvailable()` on the emulator and run a real speech test only if an offline service and locale are installed. The emulator can accept host audio, but a speech-service result is still system-image dependent.

**SmartSpectra lane:** Presage's official Android headless-test guide supports an instrumented emulator test using `useCustomInput()` and decoded, timestamped frames from a **30–60 second consented face video**. It can assert that requested pulse and breathing readings appear from the actual SDK pipeline, without camera hardware; use the published smoke test if no suitable clip is available. Keep any face clip outside Git, APK release assets, logs, and cloud test services unless rights and consent explicitly permit that use. Presage authentication still needs network. The guide says this proves integration, **not vital-sign accuracy**. `checkDeviceReadiness()` with file/custom input is inconclusive, and the emulator's simulated camera cannot validate live capture. The real front camera, lighting, frame rate, and final sensor experience require a physical phone with a person present.

## 10. Security and vulnerability analysis

This is a **design review**, not a penetration test or a claim that code is secure. The attacker may control another account, a copied share link, a malicious prescription image or document, a modified client request, or a lost phone. Assume the Android OS and its hardware key store are intact; a rooted or already-unlocked device is outside the vault's protection claim. The cloud provider can see account identities, share relationships, object sizes, and request metadata even when share content is encrypted. Apply [OWASP MASVS](https://mas.owasp.org/MASVS/) to the phone and [OWASP authorization guidance](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html) to the share service. Risk ranks below are for real patient data; the hackathon build uses synthetic data only.

| Risk | Attack or failure | Required design control | Verification before real patient use |
| --- | --- | --- | --- |
| **Critical — wrong share recipient** | A patient sends a fragment key to the wrong account or a self-declared “clinician.” | Show the exact recipient account and selected record list before encrypting. Bind the grant and authenticated encryption metadata to patient ID, recipient ID, object ID, envelope version, and expiry. The viewer must match the signed-in account to the grant. Mark clinician identity **unverified**. | Share to account B; account C with the same link cannot download. Change recipient metadata and confirm decryption fails. Human review of the confirmation screen. |

Allow patient upload only to a scoped path; deny client `SELECT` on share objects. Do not create signed download URLs. The Edge Function requires a user JWT, checks recipient ID, object ID, expiry, and revocation on every request, then uses a server-only credential to fetch ciphertext. Keep `verify_jwt` enabled; use `Cache-Control: no-store`. | Test direct Storage reads, wrong ID, guessed ID, expired and revoked grants, repeated requests, and cache headers with two accounts. ## 11. Fixed assumptions and remaining product decisions

- Android phone with API 28 or later is available for the demo. The mic demonstration needs Android 13 or later with an installed offline recognition locale. iOS is outside the hackathon build.
- Encrypted share bundles and account/share metadata may use cloud services. Plaintext records do not.
- Clinician signup is self-declared. The app does not verify a license.
- The demo uses synthetic records only. The model, OCR, and cloud design do not have clinical validation.
- Bengali and handwritten prescriptions use manual transcription in the MVP. Do not promise automatic extraction.
- The patient corrects OCR before saving. No guessed medicine names enter the record.
- The on-device model may reason over retrieved, cited record facts and a curated label pack. It cannot treat a missing fact as proof of safety. The assistant answers medicine questions with qualified, useful information.
- Booking, diagnosis, prescribing, dosage recommendations, treatment decisions, interaction-risk scoring, and live medicine scraping are outside the MVP.

The prior grill-me questions remain useful for a later product iteration. They do not block this proposed hackathon architecture. The decision with the largest product impact is the cloud boundary: if even encrypted bytes may not leave the phone, remove link sharing and use an encrypted file transfer instead.
